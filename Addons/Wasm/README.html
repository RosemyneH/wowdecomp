Writing WASM Addons (ABI v1)

Build

rustup target add wasm32-unknown-unknown
cargo build --target wasm32-unknown-unknown --release

Use the SDK in sdk/wow-addon-sdk (see examples/hello-world, inventory-watcher, ui-demo), or any language that can emit wasm32-unknown-unknown — a C example using raw imports is in examples/c-hello. Your module must export memory and wow_on_load() -> i32; export wow_on_event(ptr, len), wow_alloc/wow_free (provided by the SDK) to receive events. Importing anything outside module wow (including WASI) fails validation.

Package

MyAddon/
├── addon.toml     # [addon] id/name/version/api_version="1", [permissions], [limits]
├── addon.wasm
└── LICENSE        # optional; addon.sig is detected but not yet verified

Install by copying the folder into Interface/WasmAddOns/ in the client directory. Manifest limits are requests, clamped to host maximums. Sensitive permissions (chat.send, auction.*, storage.*, …) stay denied until the user grants them — grants persist per addon id + module hash in wasm-permissions.cfg.

Inspect & debug

In game: /script DEFAULT_CHAT_FRAME:AddMessage(WasmAddonInspectorText()) shows state, hash, granted/denied permissions, imports, memory/fuel/host-call counters and the activity log. Headless: wasm_addon_host <addon-dir> --inspector. Host functions return negative error codes (-2 permission, -3 bad memory, -4 stale handle, -6 limit, -7 buffer too small) instead of trapping your addon; traps and fuel exhaustion suspend/fault only your addon. Full status: docs/wasm-addon-progress.md.

Versioning

api_version = "1" in the manifest is checked against the host ABI. Breaking ABI changes bump the version; addons built for older versions are rejected with a clear load error rather than misbehaving.
