Data flow

Game event ──▶ FrameScript_SignalEvent ──▶ Lua listeners (unchanged order)
                                        └─▶ observer ─▶ WasmAddonManager (main thread)
                                                             ├─▶ Addon A (own Wasmtime instance + memory)
                                                             ├─▶ Addon B        ▲ fuel + StoreLimiter per callback
Host call  ◀── wow.* imports (permission-checked, memory-validated) ──────────┘
           └─▶ IWasmHostServices ─▶ client: Lua/UI layer | tests: mock host

Confirm overlay

An accepted confirm is executed by the host: chat goes through CGChat::SendNative and auction bids through CGAuctionHouse::PlaceBidNative. Each frame, WasmAddonClient_ServiceConfirms ticks the queue and applies a choice recorded by WasmConfirmUi. The prompt paints on a screen layer at z 11. Y or Enter accepts and N or Escape denies, after the 750 ms arming delay. wasmconfirm <id> accept|deny still works from the developer console.

Threading & lifetime

WasmAddonManager is main-thread only. Guest callbacks never run on worker threads; events raised reentrantly from inside a host call are queued and delivered after the current callback returns. Each addon owns one Wasmtime instance; unloading calls wow_on_unload, destroys its UI handles, clears subscriptions and drops the instance. A trap (including fuel exhaustion) faults or suspends only that addon.

Risks

  • Wasmtime is fetched prebuilt (pinned 36.0.0) when no system install exists — hash pinning is a follow-up.
  • API v2 addons receive WEV1 event payloads. Chat and unit arguments are redacted unless chat.read or units.read is granted. UNIT_*, CHAT_MSG_*, and PLAYER_* names can be subscribed.
  • Client host services depend on Lua globals (DEFAULT_CHAT_FRAME, UIParent) that appear during FrameXML load; early calls return ErrUnavailable rather than failing.
  • Windows/ARM64/macOS builds are configured from the same CMake but unverified locally.
