Lua addons to WASM

Markdown copy for GitHub: docs/lua-wasm.md.

Authoring guide for a 3.3.5 addon author moving a UI onto this client's sandboxed wasm32 runtime. Packages live in Interface/WasmAddOns. The guest is Rust (or anything that emits wasm32-unknown-unknown) linked to wow_addon_sdk. Widget helpers are wow_addon_sdk::ui. A frame is the spawn kind "frame" in that module, not a second crate.

A parallel runtime

The Lua VM is untouched. FrameXML addons still load from TOC files, and FrameScript_SignalEvent still runs every Lua listener first. A WASM package is a second runtime: its own Wasmtime instance, its own linear memory, its own fuel budget. It does not see _G, frame objects, or the Lua stack.

The host is the only thing that calls into Lua. It does that on the main thread, with lua_pcall, and only for a fixed set of operations:

  • Widgets. CreateFrame, CreateFontString, CreateTexture, then SetWidth / SetHeight / SetPoint / SetText and the other methods in the dictionary below. The guest receives a generation-tagged integer handle. The real frame stays in the Lua registry under UIParent.
  • Units. UnitExists, UnitHealth, UnitHealthMax, UnitPower, UnitPowerMax, UnitPowerType, UnitLevel, UnitClass, UnitRace, and the dead/player checks. The guest gets numbers and flags. UnitName is a separate host call and still never includes a GUID.
  • Chat display. print becomes DEFAULT_CHAT_FRAME:AddMessage. A whisper the player confirms is sent by the host (CGChat::SendNative) after the confirm dialog. The guest never calls SendChatMessage.

What the guest is allowed to see: opaque UI handles, WEV1 event arguments (nil, bool, number, text, truncated text, or Redacted), unit snapshots (health, power, level, class id, race id, flags), names from the name call, storage bytes it wrote itself, and the text it put on its own widgets. It does not see GUIDs, positions, other addons' memory, or the Lua taint state beyond the host applying a taint scope around those calls.

Package and build

One directory, copied into Interface/WasmAddOns/ in the client directory (the host also accepts a top-level WasmAddOns/ if Interface/WasmAddOns is absent):

MyPort/
├── addon.toml
└── addon.wasm
[addon]
id = "port.example"
name = "Example"
version = "0.1.0"
author = "you"
api_version = "2"

[permissions]
ui.create = true
chat.print = true
units.read = true
chat.read = true
chat.send = true
storage.read = true
storage.write = true

[limits]
memory_mb = 32
fuel = 20000000
storage_kb = 1024
max_ui_handles = 256
max_events = 128

api_version must be "2" for this contract. A v1 module relabeled as 2 fails to load. The id is lowercase letters, digits, ., -, and _.

Permissions in the manifest are a declaration, not a grant. ui.create and chat.print are available when declared. units.read, chat.read, chat.send, storage.read, storage.write, auction.read, auction.write, and combat.read stay denied until the player runs wasmgrant <id> <permission> from the developer console. Grants are stored per addon id and module hash in wasm-permissions.cfg next to the packages. A deny follows the addon id across rebuilds.

Limit keys are requests. The host clamps them: memory to 256 MB (default 32), fuel per callback to 50,000,000 (default 20,000,000), storage to 4 MB (default 1 MB), UI handles to 256, event subscriptions to 128. Unknown permission names and unknown limit keys reject the manifest.

export PATH="$HOME/.cargo/bin:$PATH"
rustup target add wasm32-unknown-unknown
cargo build --target wasm32-unknown-unknown --release

On this machine the Arch rustc has no wasm standard library. Put ~/.cargo/bin first so rustup's toolchain is the one that runs. Copy target/wasm32-unknown-unknown/release/<crate>.wasm to addon.wasm beside addon.toml. Addons/Wasm/build.sh does that for the in-tree examples and writes packages under Addons/Wasm/dist.

The crate is a cdylib depending on Addons/Wasm/sdk/wow-addon-sdk. The module must export memory. Imports outside the wow module, including WASI, fail validation.

Exports

wow_addon_v2! exports the two required callbacks. wow_on_update is optional and is not part of the macro. wow_alloc and wow_free are #[no_mangle] exports from the SDK crate; the host uses them to copy an event payload into guest memory and to free it afterward. A v2 addon that is missing wow_on_event_v2 does not finish loading. Event delivery is skipped if wow_alloc is missing.

use wow_addon_sdk::ui::*;
use wow_addon_sdk::*;

fn on_load() -> i32 {
    let _ = subscribe("PLAYER_ENTERING_WORLD");
    0
}

fn on_event(name: &str, args: &[EventArg]) -> i32 {
    let _ = (name, args);
    0
}

#[no_mangle]
pub extern "C" fn wow_on_update() -> i32 { 0 }

wow_addon_v2!(on_load, on_event);

wow_on_load runs once and must return 0. A negative return fails the addon. wow_on_event_v2 receives a WEV1 blob; the macro decodes it and calls on_event(name, args). wow_on_update, when exported, is called about five times a second (every 200 ms) on the main thread. Returning from a callback is the only way the guest runs. There is no background thread.

WEV1 argument tags, as EventArg: Nil, Bool, Number(f64), Text, Truncated(text, original_len) past 1024 bytes, Redacted. Strings in a payload are capped, and a payload that would pass 4096 bytes collapses the extra argument to Redacted.

Frozen ABI

This is the contract the ports are written against. Integers in a style blob are little-endian. Strings are pointer plus length into guest memory. A positive return from ui_spawn is a handle: high 15 bits generation, low 16 bits slot. Do not invent handles. A handle from a previous UI session is -4.

Every spawn and style call needs ui.create. A parent other than 0 must be a frame, button, or status bar this addon owns. Font strings and textures cannot be parents. The style blob is at most 64 bytes.

Anchor and justify constants in wow_addon_sdk::ui: TOPLEFT…BOTTOMRIGHT (0–8), JUSTIFY_LEFT/CENTER/RIGHT and JUSTIFY_TOP/MIDDLE/BOTTOM, STRATA_BACKGROUND (0) through STRATA_DIALOG (4). Pass 5, 6, or 7 yourself for the three higher strata.

Binding and names are host imports in module wow, same ptr/len convention as ui_set_text and units::snapshot (NUL-separated tokens):

#[link(wasm_import_module = "wow")]
extern "C" {
    fn ui_bind(handle: i32, ptr: *const u8, len: u32) -> i32;
    fn ui_get_text(handle: i32, ptr: *mut u8, cap: u32) -> i32;
    fn unit_names(ptr: *const u8, len: u32, out: *mut u8, cap: u32) -> i32;
}

After ui_bind, subscribe("WASM_UI"). In on_event, argument 0 is the event name (click, enter, leave, escape, enter_pressed, text_changed) and argument 1 is the guest handle as a number.

How a port is structured

One crate, api_version = "2", wow_addon_v2!, and wow_on_update for refresh. Build the chrome in on_load with ui.create, which does not need a sensitive grant. If units::snapshot or a chat payload comes back denied or Redacted, leave the placeholders and return 0. Do not fail on_load because units.read or chat.read is still denied. After wasmgrant, the next update or event fills the data.

fn on_load() -> i32 {
    if let Err(code) = build_chrome() { return code; }
    for event in ["PLAYER_ENTERING_WORLD", "UNIT_HEALTH", "CHAT_MSG_WHISPER"] {
        let code = subscribe(event);
        if code != 0 { return code; }
    }
    refresh()
}

fn refresh() -> i32 {
    match units::snapshot(&["player", "target"]) {
        Ok(list) => paint(&list),
        Err(_) => 0,
    }
}

fn on_event(name: &str, args: &[EventArg]) -> i32 {
    if matches!(args.first(), Some(EventArg::Redacted)) { return 0; }
    let _ = name;
    refresh()
}

#[no_mangle]
pub extern "C" fn wow_on_update() -> i32 { refresh() }

build_chrome is ordinary ui::spawn / set_size / set_point / set_backdrop. A whisper reply, once chat.send is granted, is confirm::chat_send(7, who, text). The player still has to accept the dialog (about 750 ms before Y or Enter works; N or Escape denies). History that must survive a reload goes through storage::set(storage::Scope::Character, key, bytes).

Showing ElvUI, Details, and WIM

The play client loads the original ElvUI and Details addons from Interface/AddOns. /ec is ElvUI’s options. /details is the meter. WIM is the Rust whisper port.

DetailsInterface/AddOns/DetailsDetailsBunny67’s WotLK Details, plugins included.
WIMAddons/Wasm/ports/wimport.wimWhisper windows: history plus an edit box that sends on enter.
wasmgrant port.wim chat.read
wasmgrant port.wim chat.send
wasmgrant port.wim storage.read
wasmgrant port.wim storage.write

Without chat.read, WIM still shows and whisper text stays redacted. chat.send only queues the confirm dialog; it does not skip it. Storage grants are what let WIM keep history on the character and the account.

Intentionally not Lua

  • No secure action buttons, no SecureActionButtonTemplate, no macro text, no CastSpellByName from the guest.
  • No arbitrary Lua. The guest cannot RunScript, loadstring, or call a FrameXML function by name.
  • No WASI, no files, no sockets. network.access, filesystem.access, and process.execute are not a back door; imports outside module wow are rejected.
  • No widget XML, no inherited templates, no OnUpdate script on the frame. Refresh is wow_on_update at about 5 Hz, or an event you subscribed to.
  • Texture paths are restricted to Interface\. The font file is chosen by the host.
  • Unit GUIDs never leave the host. Snapshots and unit_names are tokens, numbers, and display names.
