Nested job dispatch investigation

Confirmed API-level deadlock

A callback executing within an active job cannot call Job::Wait() successfully: RunRanges decrements remaining only after the callback returns, whereas Join waits for remaining == 0. A nested nonempty Start or ParallelFor also calls Wait before publishing, so it has the same circular dependency. A worker executing the callback additionally cannot increment its finished acknowledgement until the callback returns. See Engine/Source/Base/Job/JobSystem.cpp, functions RunRanges, WorkerMain, Join, Wait, Start and ParallelFor.

On Linux, a standalone program initialized the pool and invoked Job::ParallelFor(1, callback, nullptr), where the callback only calls Job::Wait(). Compiled against the current JobSystem.cpp with profiler stubs, it timed out after five seconds (exit 124). This establishes API-level reachability, not a production trigger. A source search finds the explicit job call sites in M2Scene.cpp, CM2SceneRender.cpp and World.cpp; their full callback call graphs have not yet been checked for indirect nested dispatch.

Next steps

Trace each callback's transitive calls before asserting game reachability. Decide and document whether nesting is unsupported or should execute inline; any change must consider callback ordering, exception behavior and lifecycle concurrency. Add a bounded regression for the chosen contract without allowing a hung test process to stall the suite.
