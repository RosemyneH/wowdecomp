Job system audit — initial lifecycle finding

Evidence refers to the working tree based on bdb5203d. This is an initial audit, not a complete call-site review.

Architecture

Engine/Source/Base/Job/JobSystem.cpp holds one global batch. Publication is under a mutex, increments an epoch and wakes every worker. Workers claim ranges using an atomic index, decrement remaining after each callback and acknowledge the epoch under the mutex. Join waits for both no remaining ranges and acknowledgments from every worker. The caller participates in ParallelFor and Wait. Start does not initially run ranges on the caller. The header prohibits callbacks from invoking Job APIs or the graphics device.

Confirmed: shutdown with active batch leaves stale completion state

Before the fix, Shutdown set shutdown and workerCount to zero without joining the batch; workers can exit before claiming their ranges and the active flag and finished counter remain set. A later Wait can deadlock because its predicate compares the stale acknowledgments against zero. Reproduction: multithreading-audit/job_lifecycle_test.cpp, built directly with JobSystem.cpp and profiler stubs. With an entered callback released during shutdown, the pre-fix binary timed out after five seconds (exit 124). API-level reachability is demonstrated; whether normal game exit reaches shutdown with an active skin batch is not yet established. Linux/Android ClientMain calls Init, CommonMain and Shutdown in WoW/Source/Linux/WinMain.cpp:32-42; asynchronous skin dispatch occurs in Engine/Source/Model2/M2Scene.cpp:1985.

Fix: Job::Shutdown calls Wait before signaling worker termination. This drains unclaimed work and waits for all workers to drop callback references while workerCount still describes the batch. Shutdown can execute a callback on its caller, consistently with Wait. This assumes lifecycle calls are serialized with dispatch on the main thread; concurrent lifecycle API support is not established.

Validation

  • c++ -std=c++17 -O2 -pthread -I. multithreading-audit/job_lifecycle_test.cpp Engine/Source/Base/Job/JobSystem.cpp -o /tmp/wow-job-lifecycle; 20 runs with a 10-second timeout passed, including active blocking callback, post-shutdown Wait, reinitialization, repeated dispatch, and immediate shutdown of active batches.
  • The same test built with -O1 -g -fsanitize=thread passed once without a reported race.
  • cmake --build build/linux --target Base -j 4 passed. Full client build and runtime are not verified. CTest lists unrelated WASM tests with missing executables; they were not run.

Confirmed: null ParallelFor callback

Engine/Source/Base/Job/JobSystem.cpp:205-227 previously checked only count, unlike Start at lines 186-188. A nonempty null callback invoked a null function pointer both without a pool and after publishing to workers. API-level reachability is demonstrated by the regression test; all current production ParallelFor sites pass named callbacks, so a production trigger has not been identified. Null and empty submissions now return without waiting, matching Start and existing empty ParallelFor semantics; callers needing completion must call Wait explicitly. The pre-fix test crashed before initialization (exit 139). After the fix, ten timeout-bounded runs passed, covering before and after initialization and an active blocked job; one ThreadSanitizer run also passed without reports, and the Base target built successfully. This is a correctness test, not a performance measurement.

Call-site investigation: grass and terrain mapped buffers

Grass preparation (WoW/Source/WorldClient/DetailDoodad.cpp:720-747) loads models and locks buffers before a synchronous ParallelFor, then unlocks on the calling thread. Its callbacks (DetailDoodad.cpp:611-623,214-228,341-395) write mapped vertex/index storage and read shared model data; they do not themselves call the graphics device in the inspected paths. The static fill array remains alive through the join. This does not establish model-data immutability or mapped-storage uniqueness.

Confirmed conditional aliasing hazard: grass uses dynamic pools (DetailDoodad.cpp:570-577), and queues multiple locks before dispatch (DetailDoodad.cpp:686-733) without checking overlap. In the OpenGL VBO dynamic path, Engine/Source/Gx/CGxDeviceOpenGL/CGxDeviceOpenGl.cpp:1097-1111 locks one shared emergency allocation per target; Engine/Source/Gx/CGxDevice/EmergencyMem.cpp:15-23 returns the same storage on subsequent locks of equal size. Multiple queued grass fills can therefore write the same memory concurrently and later unlock incorrect contents. The same emergency allocation is used on Vulkan allocation failure (Engine/Source/Gx/CGxDeviceVulkan/CGxDeviceVulkan.cpp:2739-2798). This follows from the code conditional on those backend paths and at least two eligible batches; an actual runtime trigger has not been demonstrated. Proposed solution: avoid holding multiple locks when the backend provides shared staging, preserving each lock/fill/unlock association; validate with a fake backend returning shared staging and with supported graphics runtimes. An overlap check alone after all locks is insufficient if a later lock invalidates or overwrites earlier storage.

Terrain (WoW/Source/WorldClient/MapRenderChunk.cpp:253-355) does test same-kind mapped ranges and falls back to serial RenderPrepBufs, but only after all locks; evaluate the same lock-lifetime problem and backend mapping contract separately. Calls to BufLock/BufUnlock are outside the worker callback (MapRenderChunk.cpp:169-211). No claim of full renderer safety is made.

Terrain overlap fallback: invalid buffers can be accepted without a refill

Confirmed conditional defect from source: FlushOwnedFills queues a buffer when either m_hasData or m_valid is false (MapRenderChunk.cpp:278-312). On overlap it unlocks the unfilled mappings before calling RenderPrepBufs (MapRenderChunk.cpp:324-335). On the OpenGL VBO staging path, the first unlock uploads the shared staging bytes and sets m_valid to success (CGxDeviceOpenGl.cpp:1294-1330). If that buffer already had m_hasData == 1 but was invalid, RenderPrepBufs then treats that buffer as ready and skips filling it (MapRenderChunk.cpp:1048-1063). Thus the fallback can accept stale or uninitialized staging bytes as valid. This requires overlapping queued same-target mappings and a previously populated invalid buffer; runtime occurrence is not established. Even with initially clear m_hasData, unlocking outstanding mappings interleaved with relocking can disturb the backend's per-target state.

The base device tracks only one locked buffer per target (CGxDevice.cpp:274-285), and OpenGL unlock uses the currently bound target without rebinding the buffer (CGxDeviceOpenGl.cpp:1097-1111,1317-1327). Vulkan unlock tests a single emergency lock flag per target, not a lock-specific flag (CGxDeviceVulkan.cpp:2802-2820). Consequently disjoint returned addresses alone are not proof that multiple same-target locks can safely coexist. A repair must avoid concurrent outstanding same-target backend locks unless an explicit backend contract guarantees them; validate each fill's content and validity with fake shared staging, stale-validity, and mixed staging/direct-lock cases, then test actual graphics backends. No fix or runtime verification has yet been made.

Call-site investigation: doodad culling

WoW/Source/WorldClient/World.cpp:4135-4202 constructs the work vector before dispatch; workers write separate result records, and the caller consumes them after synchronous completion. The sphere frustum function (World.cpp:2174-2180) reads the selected frustum, while the sphere occlusion query (WoW/Source/WorldClient/CWorldOcclusion.cpp:487-528) reads camera, matrices and clip buffer without explicit writes. Safety still depends on their stability and on the behavior of called math/frustum functions and other engine threads; no runtime race verification has been performed.

Terrain mitigation and verification gap

FlushOwnedFills now calls RenderPrepBufs once per pending chunk instead of acquiring same-target locks for the entire queue. Each call fills and unlocks its vertex and index mappings before the next chunk; the previous overlap detection and unfilled-unlock fallback are gone. Vertex and index locks use distinct targets. This avoids the documented queue-local lock lifetime and stale-validity path, assuming no other code concurrently locks the same target; it does not repair grass or prove general graphics-device thread safety. The Linux WorldClient target built successfully with cmake --build build/linux --target WorldClient -j 4. The existing emergency allocator and job lifecycle tests also passed, but neither exercises terrain. Fake-backend terrain regression tests, actual rendering verification and the cost of serial terrain generation remain outstanding. This intentionally sacrifices terrain fill parallelism for correctness pending a safe measured design.

Shared staging reproduction

multithreading-audit/emergency_mem_test.cpp exercises the actual EmergencyMem implementation with malloc-based Storm allocator stubs: two equal-sized locks return the same pointer, writing through the second changes the first, and a single unlock clears the shared lock flag despite two prior locks. Both c++ -std=c++17 -O2 -I. multithreading-audit/emergency_mem_test.cpp Engine/Source/Gx/CGxDevice/EmergencyMem.cpp -o /tmp/wow-emergency-test && /tmp/wow-emergency-test and the same command with -O1 -g -fsanitize=address,undefined passed on Linux x86-64. This demonstrates the underlying staging behavior, not a terrain/grass regression test, graphics runtime reproduction, or repair. A larger second lock can reallocate the array; the test does not assume that a particular allocator moves it.

Unresolved

Remaining dispatch paths, transitive callback dependencies and renderer lock contracts require ownership and thread-safety review. Init failure, concurrent public API calls, nested dispatch and callback exceptions remain unaudited. HYPOTHESIS: every-worker acknowledgment may be costly for small batches; measure before changing it.
