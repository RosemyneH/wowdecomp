Job system audit — initial lifecycle finding

Evidence refers to the working tree based on bdb5203d. This is an initial audit, not a complete call-site review.

Priority flag reads and recursive queue locking

The in-tree CAsyncObject::IsPending call is in TextureCacheGetInfo, which holds the async queue lock around the flag check and priority increase (WoW/Common/TextureCache.cpp:160-185; Engine/Source/Services/AsyncFile.cpp:77-78). The buffered-texture priority path likewise locks around its flag checks (Engine/Source/Services/Texture.cpp:1276-1290). Model priority traversal already holds that lock when it can call the texture path (Engine/Source/Model2/M2Model.cpp:1267-1292); recursive acquisition is supported by the Linux recursive pthread mutex and the Win64 Windows critical section (Engine/Source/Storm/Source/Linux/SLock.cpp:210-227; Engine/Source/Storm/Source/Win64/SLock.cpp:212-228). Replacing this lock with a non-recursive mutex without restructuring those callers could deadlock. These checks do not establish lifetime safety of the texture or its async pointer, which is accessed outside the lock; HYPOTHESIS: concurrent destruction or callback reentry could invalidate that pointer. Establish caller ownership and reproduce with controlled callbacks before modifying locking. Static analysis only.

Event scheduler close and frame serialization

EventPostCloseEx calls CloseContext, which changes active state to closed under the context lock rather than directly invoking the destroy callback (Engine/Source/Event/Event.cpp:108-123; Engine/Source/Event/EvtSched.cpp:63-72). In the ordinary scheduler path, a context is dequeued under its slot lock, processed, then either destroyed after its dispatch sequence returns or requeued (EvtSched.cpp:312-320,562-678). The shutdown cleanup drains queued contexts only when the slot's last scheduler thread exits (EvtSched.cpp:368-406,682-705). These paths support deferred destruction after the current scheduler dispatch, rather than immediate destruction from a close request, but do not prove global non-reentrancy: EventForceIdleProcessing explicitly dispatches update, poll, idle and paint on the current context (EvtSched.cpp:190-220), and handlers are invoked directly (Engine/Source/Event/EvtQueue.cpp:177-213). The previous direct-call search missed an indirect path: EventInitialize registers EventForceIdleProcessing with OsInputSetEventPollProc (Engine/Source/Event/Event.cpp:15-26). The Win32 and Win64 window procedures install a 33 ms timer for non-client right-button and system-menu messages; its callback invokes the registered procedure (Engine/Source/Os/Win32/Input.cpp:1158-1166,1529-1535; Engine/Source/Os/Win64/Input.cpp:1131-1138,1493-1499). The window procedure calls KillTimer(hwnd, 0) after chained or default processing returns (Win32/Input.cpp:1692-1699; Win64/Input.cpp:1656-1663). The Win64 input path also dispatches Windows messages from OsInputGet (Win64/Input.cpp:1207-1227). Linux and Darwin store the callback, but a source search found no invocation in those input files. This establishes a Windows indirect dispatch path, not that a timer fires during skin work or destruction; those interleavings and external callers remain unverified.

In-tree assignments to World::s_m2Scene initialize it and clear it after release during world destruction (WoW/Source/WorldClient/World.cpp:1799-1802,1834). Skin preparation is conditional on that pointer during world rendering (WoW/Source/WorldClient/CWorldSceneRender.cpp:185-194), and the later world-frame draw also checks it before the skin wait. HYPOTHESIS: a reentrant call or another allowed teardown path could release the scene between those points; these static observations do not establish reachability, nor exclude arbitrary callbacks or direct world destruction. The only in-tree direct call to CWorld::Destroy is the client destroy callback (WoW/Source/Client.cpp:1653-1660). Trace indirect teardown and dispatch reentry, and reproduce any overlap with a controlled blocked callback before altering teardown. No runtime verification is claimed.

Windows modal timer and frame ordering

The current main-thread context is set when dequeued and cleared only after the normal dispatch sequence (Engine/Source/Event/EvtSched.cpp:312-320,638-640). The scheduler calls input processing before its ordinary idle and paint; IEvtInputProcess drains OsInputGet (EvtSched.cpp:619-634; Engine/Source/Event/EvtInput.cpp:502). On Windows, OsInputGet pumps window messages, and the system-menu timer can run forced idle and paint while that input processing is suspended (Engine/Source/Os/Win64/Input.cpp:1207-1233,1493-1499). Thus a modal timer can render before the outer scheduler reaches its own paint, but this ordering alone does not put a timer inside an already-running skin preparation: a source search found OsInputGet only in the input dispatcher, and the outer dispatcher waits for that call to return. The skin batch begins during world rendering and the scene draw follows later in the same frame (WoW/Source/WorldClient/CWorldSceneRender.cpp:185-194; WoW/Source/Ui/WorldFrame.cpp:1787-1817). HYPOTHESIS: another message pump, external callback, or nested modal operation during that interval could still reenter or close the context. This search does not establish the absence of indirect platform or library message pumps; Windows runtime tracing and controlled blocked-callback reproduction remain necessary.

Normal context destruction precedes pool shutdown

The client creates an interactive event context with DestroyEngineCallback as its destroy handler (WoW/Source/Client.cpp:1791-1795). The scheduler dispatches the context destroy event from SynthesizeDestroy after the context is closed (Engine/Source/Event/EvtSched.cpp:280-295,637-649). The callback invokes ClientDestroyGame, then CWorld::Destroy, M2Destroy, and other resource teardown (Client.cpp:1653-1667); the world destructor releases the M2 scene (WoW/Source/WorldClient/World.cpp:1799-1802). On Unix and Windows the pool shutdown is later, after CommonMain returns (WoW/Source/Linux/WinMain.cpp:39-42; WoW/Source/Win64/WinMain.cpp:37-39). The asynchronous skin batch normally joins in the subsequent world-frame scene draw, but the frame returns without that draw if the scene pointer is null (WoW/Source/Ui/WorldFrame.cpp:1790-1810; Engine/Source/Model2/M2Scene.cpp:1992-1994,2602-2604).

This ordering identifies a resource teardown boundary, not a proven use-after-free: synchronous dispatches have already joined, and the usual skin draw joins before the frame returns. HYPOTHESIS: reentrant teardown or an exceptional/early frame path can leave skin callbacks active when the destroy handler releases their inputs. Establish event-context serialization and scene-pointer mutation reachability, then test with a controlled blocked skin callback before changing teardown. Static analysis only; no client runtime or Windows verification is claimed.

Exceptions escaping job callbacks

RunRanges invokes the callback without a catch and decrements the remaining count only after it returns (Engine/Source/Base/Job/JobSystem.cpp:44-58). A callback escaping a worker reaches the thread entry without a handler (JobSystem.cpp:62-84). An isolated Start test leaves the main thread yielding, ensuring the worker takes the only range; its throwing callback invoked the terminate handler with exit code 42 in ten repeated Linux runs. This does not establish that any production callback throws or cover other platforms. HYPOTHESIS: an exception caught by a caller executing a range in Wait or ParallelFor can leave completion accounting incomplete and a later join blocked (JobSystem.cpp:178-200,219-239). Reproduce that path in a bounded subprocess and audit callback throw reachability before selecting an exception policy.

Active callback at direct process exit

multithreading-audit/job_exit_repro.cpp starts one callback, waits for its entry, and calls std::exit while the callback remains blocked. Its heap-allocated input remains alive until process termination. An isolated Linux test observed the terminate handler's exit code 42 in ten repeated runs; a control releases the callback, calls Job::Shutdown, then exits normally. Both are registered in multithreading-audit/CMakeLists.txt; all six exit tests passed ten times after rebuilding job_exit_repro. This validates the isolated process behavior, not client reachability or safe teardown of actual callback resources. In particular, the control releases the callback before shutdown, so it does not establish safety of blocking callbacks during fatal exit. Storm handlers and other platforms remain untested.

Storm exit-handler registration and pool teardown

On Unix, ClientMain initializes the job pool before CommonMain and shuts it down only after that function returns (WoW/Source/Linux/WinMain.cpp:33-42). CommonMain registers the Storm exit handler indirectly through StormDestroy, after InitializeGlobal and any normal BeginCloseGame (WoW/Source/Client.cpp:1876-1881; Engine/Source/Storm/Source/Storm.cpp:44-52). Consequently, a fatal exit during initialization does not reach that registration through the normal CommonMain path. The registered handler calls StormRtlDestroy and then _exit, bypassing remaining ordinary exit handlers on Unix (Storm.cpp:21-30); on Windows it first calls _cexit, so its ordering needs separate runtime verification. This means the isolated direct-exit reproducer without Storm cannot establish actual client exit-handler ordering, and registering a pool shutdown handler without considering both registration order and callback dependencies is not a sufficient fix.

HYPOTHESIS: a normal teardown can release resources needed by an outstanding job before the later pool shutdown; trace each dispatched callback and its final barrier before proposing an earlier shutdown. Validate startup fatal exits and normal teardown in the actual client with controlled callbacks; examine other registrations and Windows behavior. Static analysis only.

Async object destruction polls a non-atomic worker flag

AsyncFileReadDestroyObject checks m_isCurrent under g_queueLock, releases the lock and repeatedly reads that plain byte while sleeping (Engine/Source/Services/AsyncFile.cpp:187-197; Engine/Source/Services/Types.h:22-24). The I/O worker clears the same byte under the lock after linking the object to the post list (AsyncFile.cpp:432-460). If destruction enters this wait while the worker completes, the unlocked read and worker write are conflicting non-atomic accesses without a happens-before relationship: a C++ data race, regardless of the sleep. Normal completion callbacks run after the worker clears the flag; AsyncFile::Cancel also defers current-object cleanup to a later callback (AsyncFile.cpp:125-146,219-239), so those paths do not by themselves demonstrate entry to the racy loop. The sequence-load destructor directly calls destruction when its async pointer is non-null (Engine/Source/Model2/M2Shared.cpp:1895-1901), but ordinary cancellation clears that pointer first (M2Shared.cpp:1940-1958).

HYPOTHESIS: a legal direct destructor or other caller can overlap a current I/O read. Trace all destruction and serialization paths and reproduce with the real worker held in a controlled read; use ThreadSanitizer where available. A candidate fix is to recheck the flag under the queue lock on each iteration, retaining the lock from the final check through unlinking; it must also address whether concurrent post-list polling can recycle the object while the destroyer sleeps. Locking the flag alone does not establish ownership or callback lifetime. Static analysis only; no runtime race reproduction is claimed.

Sequence-load destruction paths and the current-flag hypothesis

A low-priority sequence assigns its async object before submitting it and supplies loaded and unload callbacks (Engine/Source/Model2/M2Shared.cpp:2113-2186). On ordinary postload, the I/O worker has cleared m_isCurrent before the poll handler invokes the loaded callback; that callback eventually destroys the sequence-load object and hence its async object (Engine/Source/Services/AsyncFile.cpp:432-460,125-146; M2Shared.cpp:2052-2100,1896-1901). The unload callback likewise destroys the sequence-load object, but the shutdown path first joins the async workers and then drains the post list (AsyncFile.cpp:111-119,580-586; M2Shared.cpp:2103-2108). Allocation failure deletes the sequence-load node before a live async object has been submitted (M2Shared.cpp:2134-2164). Bulk cancellation nulls each async pointer before clearing the list, or defers the clear while a sequence callback is active (M2Shared.cpp:1940-1958,2093-2100). These paths do not establish a normal entry into the current-object spin loop under serialized lifecycle ownership.

HYPOTHESIS: concurrent destruction, polling, or callback reentry can violate that ownership assumption; this trace does not establish that such overlap is permitted or safe. Check sequence callback callees and shutdown ownership and reproduce using a controlled I/O worker before treating the flag race as production-reachable. Separately, CM2Model::LinkToAsyncHeadRecursive reads current/read/processed flags, but its only in-tree non-recursive entry holds the queue lock throughout recursion (Engine/Source/Model2/M2Model.cpp:1267-1292); it is not evidence of another unlocked worker-flag race on that path. Static analysis only.

UI texture replacement can release asynchronous textures

CSimpleTexture::SetTexture requests file textures with flags 0x17, which do not include the destructor's streaming flag 0x20, and closes the previous handle on replacement; its destructor closes the handle as well (Engine/Source/Frame/CSimpleRender.cpp:2214-2218,2388-2416). On a cache miss with a successfully opened BLP, the default asynchronous creation path passes those flags through to CreateBlpAsync (Engine/Source/Services/Texture.cpp:50,2219-2222,2258-2272,2516-2534). HandleClose deletes the object when the last reference is closed (Engine/Source/Base/Handle.cpp:27-32); cached or duplicated handles can retain it. Thus this provides a concrete candidate caller for the conditional deferred-cancellation accounting defect below, not a demonstration that the final close occurs while deferred.

HYPOTHESIS: replacing or destroying a UI texture before an over-budget asynchronous BLP is submitted can reach the defective subtraction. Validate with real assets and controlled budget, a cache miss and final-reference release; confirm counter and deferred-list state before and after replacement. Cache sharing, file sizes, UI timing and platform runtime remain unverified. Static analysis only.

Deferred texture destruction corrupts staging accounting

For a newly allocated async object, m_buffer is null and m_isCurrent is zero (Engine/Source/Services/AsyncFile.cpp:330-356). If CreateBlpAsync defers it because the file does not fit, no buffer allocation or counter increment occurs (Engine/Source/Services/Texture.cpp:1027-1031,2230-2251). If that texture is destroyed before submission, with the streaming flag 0x20 clear, AsyncFile::Cancel unlinks and recycles the non-current object and returns 1; the destructor nevertheless subtracts its file size from the staging counter and frees its null buffer (Texture.cpp:2114-2125; AsyncFile.cpp:219-239; Engine/Source/Storm/Source/SMem.cpp:57-64). Assuming no concurrent reuse of the recycled object, the subtraction incorrectly reduces the counter, wrapping if its size exceeds current usage; subsequent budget decisions are then wrong. This is a conditional source-level defect, not a verified production occurrence.

HYPOTHESIS: normal resource lifetime can destroy a deferred texture in this state, producing over-admission or starvation. Reproduce using the real texture and file queues, including cancellation of deferred, queued and current reads, and verify accounting and object lifetime before implementing a fix. Guarding the subtraction on a captured buffer is a candidate for the non-streaming path; separately examine streaming-flag destruction and recycled-object concurrency. Static analysis only.

Urgent texture waits can exceed the staging budget

A blocking texture request can bypass the deferred-list budget: TextureGetGxTex(..., 1, ...) calls AsyncTextureWait when no GPU texture is available, and TextureGetDimensions(..., wait) has a similar path. Both submit an unbuffered object with AsyncTextureProcess(object, 1), which allocates and adds its full size to the unsigned staging counter without a capacity check (Engine/Source/Services/Texture.cpp:98,1027-1045,1083-1096,1297-1338). The urgent flag queues the read; it does not make it synchronous (Engine/Source/Services/AsyncFile.cpp:535-565). While waiting, polling runs the texture handler before the requested object necessarily completes (AsyncFile.cpp:302-325,125-155). If the counter exceeds 4 MiB, the unsigned subtraction in both the poll handler and CreateBlpAsync wraps to a large available value, permitting additional allocations rather than enforcing the intended budget (Texture.cpp:1209-1232,2245-2251). A blocking request also provides a path for an oversized deferred texture to progress, so it is not necessarily stuck forever. Nonblocking consumers such as detail doodads request with wait 0 (WoW/Source/WorldClient/DetailDoodad.cpp:635,796).

HYPOTHESIS: a real oversized or budget-overlapping blocking request with other deferred textures can produce a transient allocation burst; file sizes, scheduling, read duration and production incidence are unverified. A saturating available calculation is a candidate for the arithmetic, but does not solve forward progress for oversized nonblocking textures; reproduce with real loading and test both progress and accounting before changing behavior. No BLP files were found in the repository checkout. Static analysis only.

Wait-all excludes deferred texture queues

CreateBlpAsync puts a texture object on s_asyncTextureList when its size exceeds the available 4 MiB staging budget, instead of submitting it to the async file queue (Engine/Source/Services/Texture.cpp:2182-2253). AsyncTextureStatus counts that list and s_asyncLoadList, but AsyncFileReadWaitAll uses status counts only for progress; its loop predicate checks current file reads, file read queues and the post list, not those texture lists (Texture.cpp:1878-1889; Engine/Source/Services/AsyncFile.cpp:617-678). The registered AsyncTextureHandler submits deferred objects only when their size fits the available budget, and runs as part of a poll (Texture.cpp:1209-1232,1893-1898; AsyncFile.cpp:149-154). If no file work is visible at the first predicate check, wait-all performs no poll and does not itself drain a deferred texture; an object larger than the entire budget also cannot fit in this handler even with no buffer in use. This is a source-level conditional behavior, not evidence that normal assets or a production caller encounter it or require those textures immediately.

HYPOTHESIS: a valid oversized texture or a deferred texture left without other file work can make a caller observe wait-all return before the texture is ready. Verify asset sizes, the texture creation paths and normal polling behavior; reproduce with actual texture loading before changing semantics. Merely adding the status count to the loop predicate risks an infinite loop for objects that cannot fit, so budget and forward progress need an explicit design. Static analysis only.

Async wait-all callback completion boundary

AsyncFileReadIsReading checks I/O threads' current objects, queued reads and the post list under the queue lock, but does not count callbacks already removed from that list (Engine/Source/Services/AsyncFile.cpp:617-640). The I/O worker moves an object from current to post list under the same lock (AsyncFile.cpp:432-460), while polling removes it under that lock and invokes its callback after releasing it (AsyncFile.cpp:125-146). AsyncFileReadWaitAll polls while that predicate is true (AsyncFile.cpp:645-678); a callback it invokes directly returns before that poll returns, but the predicate alone does not join a callback executing in a different or reentrant poll. Map non-streaming preload and load call wait-all between preparation phases (WoW/Source/WorldClient/Map.cpp:2319-2359,2541-2550,3029-3049).

HYPOTHESIS: an independently executing or nested poll could cause wait-all to return while a callback remains active, exposing incomplete state or lifetime hazards to a caller. Legal overlap and its consequences are not established; this is not a claim that normal preload is unsafe. Trace poll thread affinity and reentrancy, then reproduce with a blocked actual postload callback before choosing a completion counter or other synchronization; any change must account for callbacks that recursively poll or enqueue work. Static analysis only.

Skin-profile initialization can invoke loaded callbacks

During skin-profile completion, InitializeLoaded initializes particle emitters; geometry and recursive model names may cause SetModel or CreateChildEmittersFromModel to create another scene model (Engine/Source/Model2/M2Model.cpp:8272-8279; Engine/Source/Services/ParticleSystem2.cpp:240-248,1107-1116; Engine/Source/Model2/M2Scene.cpp:1513-1536). The recursive emitter registers a loaded callback, and registration immediately calls UpdateLoaded; it invokes the callback synchronously if IsLoaded(0, ...) succeeds (Engine/Source/Model2/M2Model.cpp:1193-1225,1297-1320). InitializeLoaded also calls UpdateLoaded before returning, while the original skin async pointer is still present (M2Model.cpp:8420-8425; Engine/Source/Model2/M2Shared.cpp:1435-1443,1707-1711). Therefore callback-driven reentry is a concrete path to investigate, not a demonstrated wait on the original object. The recursive-emitter callback calls WaitForLoad only if its model lacks the initialized flag (ParticleSystem2.cpp:1073-1099); normal initialization sets that flag before its final UpdateLoaded (M2Model.cpp:8328-8337).

HYPOTHESIS: a loaded callback, or recursive model creation involving the same shared object, can reach the earlier two-wait failure while the original callback is active. Trace cache reuse, deferred model flags and the UI loaded callback's transitive calls; reproduce with valid assets and instrumented callback sequencing before changing synchronization. Static analysis only; callback reachability, asset configurations, and legal reentry are not established.

Skin-profile completion exposes a two-wait failure path

FinishLoadingSkinProfile sets shared flag 2 before iterating the callback list and calling each model's InitializeLoaded; the shared async pointer is only cleared after that function returns and its object is destroyed (Engine/Source/Model2/M2Shared.cpp:1416-1443,1707-1711). An overlapping or reentrant CM2Model::WaitForLoad tests the same pointer twice and calls AsyncFileReadWait each time (Engine/Source/Model2/M2Model.cpp:730-741). If the first wait enters while the object is processed and remains valid and unchanged until the second check, the first returns without decrementing its static nesting guard and the second reaches the fatal guard (Engine/Source/Services/AsyncFile.cpp:274-289). If completion instead destroys the object concurrently, lifetime and synchronization must be resolved first; the conditional sequence is not a safe concurrency contract.

HYPOTHESIS: a legal callback reentry or independent caller can reach that interval. The source establishes the conditional failure, not such a caller or actual crash. Inspect transitive calls from InitializeSkinProfile and InitializeLoaded for reentry and their calling-thread ownership, then reproduce with a held real callback; simply balancing the guard would not wait for model initialization or make concurrent pointer access safe. Static analysis only.

Model skin-profile async wait ownership

Model skin-profile loading allocates an async object, stores it in the shared model and registers SkinProfileLoadedCallback (Engine/Source/Model2/M2Shared.cpp:1726-1754). Polling marks that object processed before the callback begins (Engine/Source/Services/AsyncFile.cpp:125-146); the callback calls FinishLoadingSkinProfile before destroying the object and clearing the shared pointer (M2Shared.cpp:1707-1711). A model instance's WaitForLoad checks that shared pointer and passes it to AsyncFileReadWait (Engine/Source/Model2/M2Model.cpp:730-737). This identifies another concrete owner and interval for the previously documented processed-before-completion hazard; it does not establish a legal concurrent or reentrant waiter. HYPOTHESIS: a waiter that accesses the still-live object during profile completion can return early, poison the nesting guard, and observe incomplete model state. Trace the profile completion callees and caller thread affinity, then reproduce with the real callback held before destruction; a synthetic state test alone would not establish production reachability. Static analysis only.

Area purge versus postload ownership

Out-of-range area eviction in CMap::PreUpdateAreas purges an area when its async object is absent or not current (WoW/Source/WorldClient/Map.cpp:2015-2030); map preparation, reload and unload also reach bulk purge (Map.cpp:2308-2310,2541,3029,5913). Both purge paths call CMapArea::Purge and then destroy and return the area to its object heap (Map.cpp:3111-3114,4012-4029). For a non-current async object, Cancel unlinks and recycles the object without waiting for an already-dequeued callback (Engine/Source/Services/AsyncFile.cpp:219-235), while polling unlocks before reading its callback and argument (AsyncFile.cpp:138-146). Area postload dereferences the area, its file buffer and its async object (WoW/Source/WorldClient/MapArea.cpp:307-350). Thus queue locking alone does not establish area or async-object lifetime across callback execution. HYPOTHESIS: concurrent or reentrant purge in that interval can cause recycled-object access or use-after-free; production overlap and exact interleavings have not been demonstrated. Ordinary eviction and direct waits are both in the synchronous preparation path, but that is not a global thread-affinity guarantee. Validate caller serialization and use a blocked real callback with teardown under a race detector before choosing a lifetime protocol. Static analysis only.

Separately, AsyncFileReadWait increments its static nesting guard before returning early for an already-processed object, without decrementing it (AsyncFile.cpp:274-287,316-325). The next wait would enter the fatal-error branch. The processed state is set before postload invocation, but whether a valid production caller can pass such an object remains unproven; its callback may destroy and recycle it. HYPOTHESIS: overlapping or reentrant waits can reach the early return. Reproduce with valid object lifetime and investigate the guard's thread-safety before changing behavior.

Processed does not mean callback complete

The poll handler sets m_isProcessed and releases the queue lock before invoking postload (Engine/Source/Services/AsyncFile.cpp:125-146). The area callback keeps its async pointer until after chunk processing and object destruction (WoW/Source/WorldClient/MapArea.cpp:344-350); the texture success callback similarly keeps it through texture processing and cleanup (Engine/Source/Services/Texture.cpp:1859-1874). Thus a processed object can remain associated with a live owner while its callback is in progress. A concurrent waiter that can validly access that object would return without waiting for callback completion and leave the nesting guard incremented; a later wait enters the fatal branch. On Linux that branch exits the process (Engine/Source/Storm/Source/Linux/SErr.cpp:647-682). HYPOTHESIS: such a concurrent waiter is reachable in production; neither object lifetime nor legal concurrent access has been established. The guard itself is a non-atomic static outside the queue lock, so concurrent calls are not a supported synchronization protocol and can race. Simply balancing the guard would not establish completion or object lifetime. Validate thread affinity and reproduce with a deliberately blocked callback and a waiter before designing a completion protocol; static inspection only.

Async area loading and callback execution

CMapArea::Load submits a file read with AsyncCallback and an area pointer (WoW/Source/WorldClient/MapArea.cpp:383-393). The async I/O thread reads into the supplied buffer, then places the object on the post list under the queue lock; it does not itself invoke the postload callback (Engine/Source/Services/AsyncFile.cpp:405-470). AsyncFileReadPollHandler unlinks an object and marks it processed under the lock, releases the lock, and invokes its postload callback on the polling caller (AsyncFile.cpp:125-150). Area postload parses chunks, loads textures, destroys the async object, and clears the area's async pointer (MapArea.cpp:307-350); the inspected callback does not itself create terrain or WMO model references.

Polling is registered for the poll event (AsyncFile.cpp:493-505; Engine/Source/Event/EvtSched.cpp:158-166), but is also called directly by waits and map-loading code (AsyncFile.cpp:274-325,645-657; WoW/Source/WorldClient/Map.cpp:2374-2454). In area preparation, a requested wait runs the poll handler, and once the async pointer is cleared, the caller can synchronously update the area (Map.cpp:2058-2087). Consequently, the I/O worker's post-list publication is not evidence of model construction on that worker; neither does this establish exclusive main-thread polling or rule out reentrancy. CMapArea::Purge cancels an outstanding object and delegates buffer cleanup when a read is current (MapArea.cpp:29-55; AsyncFile.cpp:217-235), but poll callbacks execute outside the queue lock, so lifetime safety still depends on caller serialization. HYPOTHESIS: concurrent purge and polling could invalidate callback-owned area state; no production concurrent invocation has been established. Trace poll and purge thread affinity and reentrancy, then exercise a blocked callback with concurrent teardown under a race detector before selecting synchronization changes. Static inspection only; no runtime verification.

Architecture

Engine/Source/Base/Job/JobSystem.cpp holds one global batch. Publication is under a mutex, increments an epoch and wakes every worker. Workers claim ranges using an atomic index, decrement remaining after each callback and acknowledge the epoch under the mutex. Join waits for both no remaining ranges and acknowledgments from every worker. The caller participates in ParallelFor and Wait. Start does not initially run ranges on the caller. The header prohibits callbacks from invoking Job APIs or the graphics device.

Confirmed: shutdown with active batch leaves stale completion state

Before the fix, Shutdown set shutdown and workerCount to zero without joining the batch; workers can exit before claiming their ranges and the active flag and finished counter remain set. A later Wait can deadlock because its predicate compares the stale acknowledgments against zero. Reproduction: multithreading-audit/job_lifecycle_test.cpp, built directly with JobSystem.cpp and profiler stubs. With an entered callback released during shutdown, the pre-fix binary timed out after five seconds (exit 124). API-level reachability is demonstrated; whether normal game exit reaches shutdown with an active skin batch is not yet established. Linux/Android ClientMain calls Init, CommonMain and Shutdown in WoW/Source/Linux/WinMain.cpp:32-42; asynchronous skin dispatch occurs in Engine/Source/Model2/M2Scene.cpp:1985.

Fix: Job::Shutdown calls Wait before signaling worker termination. This drains unclaimed work and waits for all workers to drop callback references while workerCount still describes the batch. Shutdown can execute a callback on its caller, consistently with Wait. This assumes lifecycle calls are serialized with dispatch on the main thread; concurrent lifecycle API support is not established.

Validation

  • c++ -std=c++17 -O2 -pthread -I. multithreading-audit/job_lifecycle_test.cpp Engine/Source/Base/Job/JobSystem.cpp -o /tmp/wow-job-lifecycle; 20 runs with a 10-second timeout passed, including active blocking callback, post-shutdown Wait, reinitialization, repeated dispatch, and immediate shutdown of active batches.
  • The same test built with -O1 -g -fsanitize=thread passed once without a reported race.
  • cmake --build build/linux --target Base -j 4 passed. Full client build and runtime are not verified. CTest lists unrelated WASM tests with missing executables; they were not run.

Confirmed: null ParallelFor callback

Engine/Source/Base/Job/JobSystem.cpp:205-227 previously checked only count, unlike Start at lines 186-188. A nonempty null callback invoked a null function pointer both without a pool and after publishing to workers. API-level reachability is demonstrated by the regression test; all current production ParallelFor sites pass named callbacks, so a production trigger has not been identified. Null and empty submissions now return without waiting, matching Start and existing empty ParallelFor semantics; callers needing completion must call Wait explicitly. The pre-fix test crashed before initialization (exit 139). After the fix, ten timeout-bounded runs passed, covering before and after initialization and an active blocked job; one ThreadSanitizer run also passed without reports, and the Base target built successfully. This is a correctness test, not a performance measurement.

Call-site investigation: grass and terrain mapped buffers

Grass preparation (WoW/Source/WorldClient/DetailDoodad.cpp:720-747) loads models and locks buffers before a synchronous ParallelFor, then unlocks on the calling thread. Its callbacks (DetailDoodad.cpp:611-623,214-228,341-395) write mapped vertex/index storage and read shared model data; they do not themselves call the graphics device in the inspected paths. The static fill array remains alive through the join. This does not establish model-data immutability or mapped-storage uniqueness.

Confirmed conditional aliasing hazard: grass uses dynamic pools (DetailDoodad.cpp:570-577), and queues multiple locks before dispatch (DetailDoodad.cpp:686-733) without checking overlap. In the OpenGL VBO dynamic path, Engine/Source/Gx/CGxDeviceOpenGL/CGxDeviceOpenGl.cpp:1097-1111 locks one shared emergency allocation per target; Engine/Source/Gx/CGxDevice/EmergencyMem.cpp:15-23 returns the same storage on subsequent locks of equal size. Multiple queued grass fills can therefore write the same memory concurrently and later unlock incorrect contents. The same emergency allocation is used on Vulkan allocation failure (Engine/Source/Gx/CGxDeviceVulkan/CGxDeviceVulkan.cpp:2739-2798). This follows from the code conditional on those backend paths and at least two eligible batches; an actual runtime trigger has not been demonstrated. An overlap check alone after all locks is insufficient if a later lock invalidates or overwrites earlier storage.

Terrain (WoW/Source/WorldClient/MapRenderChunk.cpp:253-355) does test same-kind mapped ranges and falls back to serial RenderPrepBufs, but only after all locks; evaluate the same lock-lifetime problem and backend mapping contract separately. Terrain overlap fallback: invalid buffers can be accepted without a refill

Confirmed conditional defect from source: FlushOwnedFills queues a buffer when either m_hasData or m_valid is false (MapRenderChunk.cpp:278-312). On overlap it unlocks the unfilled mappings before calling RenderPrepBufs (MapRenderChunk.cpp:324-335). On the OpenGL VBO staging path, the first unlock uploads the shared staging bytes and sets m_valid to success (CGxDeviceOpenGl.cpp:1294-1330). If that buffer already had m_hasData == 1 but was invalid, RenderPrepBufs then treats that buffer as ready and skips filling it (MapRenderChunk.cpp:1048-1063). Thus the fallback can accept stale or uninitialized staging bytes as valid. This requires overlapping queued same-target mappings and a previously populated invalid buffer; runtime occurrence is not established. Even with initially clear m_hasData, unlocking outstanding mappings interleaved with relocking can disturb the backend's per-target state.

The base device tracks only one locked buffer per target (CGxDevice.cpp:274-285), and OpenGL unlock uses the currently bound target without rebinding the buffer (CGxDeviceOpenGl.cpp:1097-1111,1317-1327). Vulkan unlock tests a single emergency lock flag per target, not a lock-specific flag (CGxDeviceVulkan.cpp:2802-2820). Consequently disjoint returned addresses alone are not proof that multiple same-target locks can safely coexist. A repair must avoid concurrent outstanding same-target backend locks unless an explicit backend contract guarantees them; validate each fill's content and validity with fake shared staging, stale-validity, and mixed staging/direct-lock cases, then test actual graphics backends. The queue-local mitigation described below has since been implemented; actual backend runtime verification remains outstanding.

Lifecycle gap: non-Unix entry points do not shut down the pool

Confirmed API-level failure: the process-global pool contains joinable std::thread objects after Job::Init (Engine/Source/Base/Job/JobSystem.cpp:15-33,99-110); returning from main without Job::Shutdown destroys those objects and invokes std::terminate. The tracked job_exit_repro.cpp installs a terminate handler that exits 42. On Linux, compiling it with c++ -std=c++17 -O2 -pthread -I. multithreading-audit/job_exit_repro.cpp Engine/Source/Base/Job/JobSystem.cpp -o /tmp/wow-job-exit-repro yielded exit 42 without arguments and exit 0 with shutdown. This isolated process demonstrates the C++ lifecycle defect, not an actual client exit.

Unix and Android call Init, CommonMain, then Shutdown (WoW/Source/Linux/WinMain.cpp:33-42); Windows x86/x64 and Darwin return from CommonMain without those calls (WoW/Source/Win32/WinMain.cpp:30-36, WoW/Source/Win64/WinMain.cpp:29-36, WoW/Source/Darwin/WinMain.cpp:9-20). World initialization calls CMap::Initialize, which initializes terrain and the pool (WoW/Source/WorldClient/World.cpp:1857-1859, WoW/Source/WorldClient/Map.cpp:688-693, WoW/Source/WorldClient/MapChunk.cpp:283-285, WoW/Source/WorldClient/MapRenderChunk.cpp:264-265); repository source search found no production Shutdown outside the Unix entry point. Thus a normal return after reaching world initialization is a conditional source-level trigger on these non-Unix entry points; platform runtime behavior and whether client teardown always reaches normal process destruction have not been tested.

Candidate repair: pair lifecycle management at each supported client entry point, and verify shutdown occurs before callback-owned state is destroyed; do not merely rely on global destruction because cross-translation-unit destruction order and outstanding callbacks are unsafe. Add exit-process regression coverage and test supported Windows and Darwin builds and runtime shutdown. The current Unix shutdown is after CommonMain teardown, so whether an outstanding asynchronous skin batch can retain already-destroyed data remains an independent open question.

Trace remaining creation paths and reproduce under a race detector before selecting a fix; no runtime test was performed.

SIMD skin transform ownership

WriteSkin selects a transform by bone influence and, for optimized geometry, walks enabled batch sections (Engine/Source/Model2/M2Scene.cpp:1824-1883). The SSE implementations fall back to scalar for unaligned output and otherwise read vertices and bone matrices, keeping blended rows local and writing the supplied output (Engine/Source/Model2/M2Model.cpp:3885-3960). AVX2's blend/cache and pair helpers likewise use caller-local rows and output pointers (Engine/Source/Model2/M2SkinAvx2.cpp:20-91,110-155). The vector stores temporarily overwrite adjacent fields inside each eight-float output vertex, subsequently overwritten by normal and texture stores; they do not extend beyond that vertex. These paths do not themselves mutate model state in the inspected code. This conclusion assumes valid section counts, indices, aligned bone matrices and disjoint correctly sized output regions, and does not establish source immutability or object lifetime during the overlap.

The function table is lazily initialized without synchronization in the model constructor (M2Model.cpp:4617-4640); a first model must already exist for a skin job to be prepared. HYPOTHESIS: concurrent construction during the first initialization could race on that table; constructor thread ownership and first-construction ordering have not been established. Verify model construction call paths and use a focused race test before treating this as a reachable defect or changing initialization. Validate the skin variants with representative model data and race instrumentation across the overlap; no runtime test or SIMD output equivalence measurement was performed here.
