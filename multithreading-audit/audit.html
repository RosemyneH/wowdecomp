Job system audit — initial lifecycle finding

Evidence refers to the working tree based on bdb5203d. This is an initial audit, not a complete call-site review.

Deferred texture destruction corrupts staging accounting

For a newly allocated async object, m_buffer is null and m_isCurrent is zero (Engine/Source/Services/AsyncFile.cpp:330-356). If CreateBlpAsync defers it because the file does not fit, no buffer allocation or counter increment occurs (Engine/Source/Services/Texture.cpp:1027-1031,2230-2251). If that texture is destroyed before submission, with the streaming flag 0x20 clear, AsyncFile::Cancel unlinks and recycles the non-current object and returns 1; the destructor nevertheless subtracts its file size from the staging counter and frees its null buffer (Texture.cpp:2114-2125; AsyncFile.cpp:219-239; Engine/Source/Storm/Source/SMem.cpp:57-64). Assuming no concurrent reuse of the recycled object, the subtraction incorrectly reduces the counter, wrapping if its size exceeds current usage; subsequent budget decisions are then wrong. This is a conditional source-level defect, not a verified production occurrence.

HYPOTHESIS: normal resource lifetime can destroy a deferred texture in this state, producing over-admission or starvation. Reproduce using the real texture and file queues, including cancellation of deferred, queued and current reads, and verify accounting and object lifetime before implementing a fix. Guarding the subtraction on a captured buffer is a candidate for the non-streaming path; separately examine streaming-flag destruction and recycled-object concurrency. Static analysis only.

Urgent texture waits can exceed the staging budget

A blocking texture request can bypass the deferred-list budget: TextureGetGxTex(..., 1, ...) calls AsyncTextureWait when no GPU texture is available, and TextureGetDimensions(..., wait) has a similar path. Both submit an unbuffered object with AsyncTextureProcess(object, 1), which allocates and adds its full size to the unsigned staging counter without a capacity check (Engine/Source/Services/Texture.cpp:98,1027-1045,1083-1096,1297-1338). The urgent flag queues the read; it does not make it synchronous (Engine/Source/Services/AsyncFile.cpp:535-565). While waiting, polling runs the texture handler before the requested object necessarily completes (AsyncFile.cpp:302-325,125-155). If the counter exceeds 4 MiB, the unsigned subtraction in both the poll handler and CreateBlpAsync wraps to a large available value, permitting additional allocations rather than enforcing the intended budget (Texture.cpp:1209-1232,2245-2251). A blocking request also provides a path for an oversized deferred texture to progress, so it is not necessarily stuck forever. Nonblocking consumers such as detail doodads request with wait 0 (WoW/Source/WorldClient/DetailDoodad.cpp:635,796).

HYPOTHESIS: a real oversized or budget-overlapping blocking request with other deferred textures can produce a transient allocation burst; file sizes, scheduling, read duration and production incidence are unverified. A saturating available calculation is a candidate for the arithmetic, but does not solve forward progress for oversized nonblocking textures; reproduce with real loading and test both progress and accounting before changing behavior. No BLP files were found in the repository checkout. Static analysis only.

Wait-all excludes deferred texture queues

CreateBlpAsync puts a texture object on s_asyncTextureList when its size exceeds the available 4 MiB staging budget, instead of submitting it to the async file queue (Engine/Source/Services/Texture.cpp:2182-2253). AsyncTextureStatus counts that list and s_asyncLoadList, but AsyncFileReadWaitAll uses status counts only for progress; its loop predicate checks current file reads, file read queues and the post list, not those texture lists (Texture.cpp:1878-1889; Engine/Source/Services/AsyncFile.cpp:617-678). The registered AsyncTextureHandler submits deferred objects only when their size fits the available budget, and runs as part of a poll (Texture.cpp:1209-1232,1893-1898; AsyncFile.cpp:149-154). If no file work is visible at the first predicate check, wait-all performs no poll and does not itself drain a deferred texture; an object larger than the entire budget also cannot fit in this handler even with no buffer in use. This is a source-level conditional behavior, not evidence that normal assets or a production caller encounter it or require those textures immediately.

HYPOTHESIS: a valid oversized texture or a deferred texture left without other file work can make a caller observe wait-all return before the texture is ready. Verify asset sizes, the texture creation paths and normal polling behavior; reproduce with actual texture loading before changing semantics. Merely adding the status count to the loop predicate risks an infinite loop for objects that cannot fit, so budget and forward progress need an explicit design. Static analysis only.

Async wait-all callback completion boundary

AsyncFileReadIsReading checks I/O threads' current objects, queued reads and the post list under the queue lock, but does not count callbacks already removed from that list (Engine/Source/Services/AsyncFile.cpp:617-640). The I/O worker moves an object from current to post list under the same lock (AsyncFile.cpp:432-460), while polling removes it under that lock and invokes its callback after releasing it (AsyncFile.cpp:125-146). AsyncFileReadWaitAll polls while that predicate is true (AsyncFile.cpp:645-678); a callback it invokes directly returns before that poll returns, but the predicate alone does not join a callback executing in a different or reentrant poll. Map non-streaming preload and load call wait-all between preparation phases (WoW/Source/WorldClient/Map.cpp:2319-2359,2541-2550,3029-3049).

HYPOTHESIS: an independently executing or nested poll could cause wait-all to return while a callback remains active, exposing incomplete state or lifetime hazards to a caller. Legal overlap and its consequences are not established; this is not a claim that normal preload is unsafe. Trace poll thread affinity and reentrancy, then reproduce with a blocked actual postload callback before choosing a completion counter or other synchronization; any change must account for callbacks that recursively poll or enqueue work. Static analysis only.

Model skin-profile async wait ownership

Model skin-profile loading allocates an async object, stores it in the shared model and registers SkinProfileLoadedCallback (Engine/Source/Model2/M2Shared.cpp:1726-1754). Polling marks that object processed before the callback begins (Engine/Source/Services/AsyncFile.cpp:125-146); the callback calls FinishLoadingSkinProfile before destroying the object and clearing the shared pointer (M2Shared.cpp:1707-1711). A model instance's WaitForLoad checks that shared pointer and passes it to AsyncFileReadWait (Engine/Source/Model2/M2Model.cpp:730-737). This identifies another concrete owner and interval for the previously documented processed-before-completion hazard; it does not establish a legal concurrent or reentrant waiter. HYPOTHESIS: a waiter that accesses the still-live object during profile completion can return early, poison the nesting guard, and observe incomplete model state. Trace the profile completion callees and caller thread affinity, then reproduce with the real callback held before destruction; a synthetic state test alone would not establish production reachability. Static analysis only.

Area purge versus postload ownership

Out-of-range area eviction in CMap::PreUpdateAreas purges an area when its async object is absent or not current (WoW/Source/WorldClient/Map.cpp:2015-2030); map preparation, reload and unload also reach bulk purge (Map.cpp:2308-2310,2541,3029,5913). Both purge paths call CMapArea::Purge and then destroy and return the area to its object heap (Map.cpp:3111-3114,4012-4029). For a non-current async object, Cancel unlinks and recycles the object without waiting for an already-dequeued callback (Engine/Source/Services/AsyncFile.cpp:219-235), while polling unlocks before reading its callback and argument (AsyncFile.cpp:138-146). Area postload dereferences the area, its file buffer and its async object (WoW/Source/WorldClient/MapArea.cpp:307-350). Thus queue locking alone does not establish area or async-object lifetime across callback execution. HYPOTHESIS: concurrent or reentrant purge in that interval can cause recycled-object access or use-after-free; production overlap and exact interleavings have not been demonstrated. Ordinary eviction and direct waits are both in the synchronous preparation path, but that is not a global thread-affinity guarantee. Validate caller serialization and use a blocked real callback with teardown under a race detector before choosing a lifetime protocol. Static analysis only.

Separately, AsyncFileReadWait increments its static nesting guard before returning early for an already-processed object, without decrementing it (AsyncFile.cpp:274-287,316-325). The next wait would enter the fatal-error branch. The processed state is set before postload invocation, but whether a valid production caller can pass such an object remains unproven; its callback may destroy and recycle it. HYPOTHESIS: overlapping or reentrant waits can reach the early return. Reproduce with valid object lifetime and investigate the guard's thread-safety before changing behavior.

Processed does not mean callback complete

The poll handler sets m_isProcessed and releases the queue lock before invoking postload (Engine/Source/Services/AsyncFile.cpp:125-146). The area callback keeps its async pointer until after chunk processing and object destruction (WoW/Source/WorldClient/MapArea.cpp:344-350); the texture success callback similarly keeps it through texture processing and cleanup (Engine/Source/Services/Texture.cpp:1859-1874). Thus a processed object can remain associated with a live owner while its callback is in progress. A concurrent waiter that can validly access that object would return without waiting for callback completion and leave the nesting guard incremented; a later wait enters the fatal branch. On Linux that branch exits the process (Engine/Source/Storm/Source/Linux/SErr.cpp:647-682). HYPOTHESIS: such a concurrent waiter is reachable in production; neither object lifetime nor legal concurrent access has been established. The guard itself is a non-atomic static outside the queue lock, so concurrent calls are not a supported synchronization protocol and can race. Simply balancing the guard would not establish completion or object lifetime. Validate thread affinity and reproduce with a deliberately blocked callback and a waiter before designing a completion protocol; static inspection only.

Async area loading and callback execution

CMapArea::Load submits a file read with AsyncCallback and an area pointer (WoW/Source/WorldClient/MapArea.cpp:383-393). The async I/O thread reads into the supplied buffer, then places the object on the post list under the queue lock; it does not itself invoke the postload callback (Engine/Source/Services/AsyncFile.cpp:405-470). AsyncFileReadPollHandler unlinks an object and marks it processed under the lock, releases the lock, and invokes its postload callback on the polling caller (AsyncFile.cpp:125-150). Area postload parses chunks, loads textures, destroys the async object, and clears the area's async pointer (MapArea.cpp:307-350); the inspected callback does not itself create terrain or WMO model references.

Polling is registered for the poll event (AsyncFile.cpp:493-505; Engine/Source/Event/EvtSched.cpp:158-166), but is also called directly by waits and map-loading code (AsyncFile.cpp:274-325,645-657; WoW/Source/WorldClient/Map.cpp:2374-2454). In area preparation, a requested wait runs the poll handler, and once the async pointer is cleared, the caller can synchronously update the area (Map.cpp:2058-2087). Consequently, the I/O worker's post-list publication is not evidence of model construction on that worker; neither does this establish exclusive main-thread polling or rule out reentrancy. CMapArea::Purge cancels an outstanding object and delegates buffer cleanup when a read is current (MapArea.cpp:29-55; AsyncFile.cpp:217-235), but poll callbacks execute outside the queue lock, so lifetime safety still depends on caller serialization. HYPOTHESIS: concurrent purge and polling could invalidate callback-owned area state; no production concurrent invocation has been established. Trace poll and purge thread affinity and reentrancy, then exercise a blocked callback with concurrent teardown under a race detector before selecting synchronization changes. Static inspection only; no runtime verification.

Architecture

Engine/Source/Base/Job/JobSystem.cpp holds one global batch. Publication is under a mutex, increments an epoch and wakes every worker. Workers claim ranges using an atomic index, decrement remaining after each callback and acknowledge the epoch under the mutex. Join waits for both no remaining ranges and acknowledgments from every worker. The caller participates in ParallelFor and Wait. Start does not initially run ranges on the caller. The header prohibits callbacks from invoking Job APIs or the graphics device.

Confirmed: shutdown with active batch leaves stale completion state

Before the fix, Shutdown set shutdown and workerCount to zero without joining the batch; workers can exit before claiming their ranges and the active flag and finished counter remain set. A later Wait can deadlock because its predicate compares the stale acknowledgments against zero. Reproduction: multithreading-audit/job_lifecycle_test.cpp, built directly with JobSystem.cpp and profiler stubs. With an entered callback released during shutdown, the pre-fix binary timed out after five seconds (exit 124). API-level reachability is demonstrated; whether normal game exit reaches shutdown with an active skin batch is not yet established. Linux/Android ClientMain calls Init, CommonMain and Shutdown in WoW/Source/Linux/WinMain.cpp:32-42; asynchronous skin dispatch occurs in Engine/Source/Model2/M2Scene.cpp:1985.

Fix: Job::Shutdown calls Wait before signaling worker termination. This drains unclaimed work and waits for all workers to drop callback references while workerCount still describes the batch. Shutdown can execute a callback on its caller, consistently with Wait. This assumes lifecycle calls are serialized with dispatch on the main thread; concurrent lifecycle API support is not established.

  • cmake --build build/linux --target Base -j 4 passed. Full client build and runtime are not verified. CTest lists unrelated WASM tests with missing executables; they were not run.

Confirmed: null ParallelFor callback

Engine/Source/Base/Job/JobSystem.cpp:205-227 previously checked only count, unlike Start at lines 186-188. A nonempty null callback invoked a null function pointer both without a pool and after publishing to workers. API-level reachability is demonstrated by the regression test; all current production ParallelFor sites pass named callbacks, so a production trigger has not been identified. Null and empty submissions now return without waiting, matching Start and existing empty ParallelFor semantics; callers needing completion must call Wait explicitly. The pre-fix test crashed before initialization (exit 139). After the fix, ten timeout-bounded runs passed, covering before and after initialization and an active blocked job; one ThreadSanitizer run also passed without reports, and the Base target built successfully. This is a correctness test, not a performance measurement.

Call-site investigation: grass and terrain mapped buffers

Grass preparation (WoW/Source/WorldClient/DetailDoodad.cpp:720-747) loads models and locks buffers before a synchronous ParallelFor, then unlocks on the calling thread. Its callbacks (DetailDoodad.cpp:611-623,214-228,341-395) write mapped vertex/index storage and read shared model data; they do not themselves call the graphics device in the inspected paths. The static fill array remains alive through the join. This does not establish model-data immutability or mapped-storage uniqueness.

Confirmed conditional aliasing hazard: grass uses dynamic pools (DetailDoodad.cpp:570-577), and queues multiple locks before dispatch (DetailDoodad.cpp:686-733) without checking overlap. In the OpenGL VBO dynamic path, Engine/Source/Gx/CGxDeviceOpenGL/CGxDeviceOpenGl.cpp:1097-1111 locks one shared emergency allocation per target; Engine/Source/Gx/CGxDevice/EmergencyMem.cpp:15-23 returns the same storage on subsequent locks of equal size. Multiple queued grass fills can therefore write the same memory concurrently and later unlock incorrect contents. The same emergency allocation is used on Vulkan allocation failure (Engine/Source/Gx/CGxDeviceVulkan/CGxDeviceVulkan.cpp:2739-2798). This follows from the code conditional on those backend paths and at least two eligible batches; an actual runtime trigger has not been demonstrated. Proposed solution: avoid holding multiple locks when the backend provides shared staging, preserving each lock/fill/unlock association; validate with a fake backend returning shared staging and with supported graphics runtimes. An overlap check alone after all locks is insufficient if a later lock invalidates or overwrites earlier storage.

Terrain (WoW/Source/WorldClient/MapRenderChunk.cpp:253-355) does test same-kind mapped ranges and falls back to serial RenderPrepBufs, but only after all locks; evaluate the same lock-lifetime problem and backend mapping contract separately. Calls to BufLock/BufUnlock are outside the worker callback (MapRenderChunk.cpp:169-211). No claim of full renderer safety is made.

Terrain overlap fallback: invalid buffers can be accepted without a refill

Confirmed conditional defect from source: FlushOwnedFills queues a buffer when either m_hasData or m_valid is false (MapRenderChunk.cpp:278-312). On overlap it unlocks the unfilled mappings before calling RenderPrepBufs (MapRenderChunk.cpp:324-335). On the OpenGL VBO staging path, the first unlock uploads the shared staging bytes and sets m_valid to success (CGxDeviceOpenGl.cpp:1294-1330). If that buffer already had m_hasData == 1 but was invalid, RenderPrepBufs then treats that buffer as ready and skips filling it (MapRenderChunk.cpp:1048-1063). Thus the fallback can accept stale or uninitialized staging bytes as valid. This requires overlapping queued same-target mappings and a previously populated invalid buffer; runtime occurrence is not established. Even with initially clear m_hasData, unlocking outstanding mappings interleaved with relocking can disturb the backend's per-target state.

The base device tracks only one locked buffer per target (CGxDevice.cpp:274-285), and OpenGL unlock uses the currently bound target without rebinding the buffer (CGxDeviceOpenGl.cpp:1097-1111,1317-1327). Vulkan unlock tests a single emergency lock flag per target, not a lock-specific flag (CGxDeviceVulkan.cpp:2802-2820). Consequently disjoint returned addresses alone are not proof that multiple same-target locks can safely coexist. A repair must avoid concurrent outstanding same-target backend locks unless an explicit backend contract guarantees them; validate each fill's content and validity with fake shared staging, stale-validity, and mixed staging/direct-lock cases, then test actual graphics backends. The queue-local mitigation described below has since been implemented; actual backend runtime verification remains outstanding.

Call-site investigation: doodad culling

WoW/Source/WorldClient/World.cpp:4135-4202 constructs the work vector before dispatch; workers write separate result records, and the caller consumes them after synchronous completion. The sphere frustum function (World.cpp:2174-2180) reads the selected frustum, while the sphere occlusion query (WoW/Source/WorldClient/CWorldOcclusion.cpp:487-528) reads camera, matrices and clip buffer without explicit writes. Safety still depends on their stability and on the behavior of called math/frustum functions and other engine threads; no runtime race verification has been performed.

Terrain mitigation and verification gap

FlushOwnedFills now calls RenderPrepBufs once per pending chunk instead of acquiring same-target locks for the entire queue. Each call fills and unlocks its vertex and index mappings before the next chunk; the previous overlap detection and unfilled-unlock fallback are gone. Vertex and index locks use distinct targets. This avoids the documented queue-local lock lifetime and stale-validity path, assuming no other code concurrently locks the same target; it does not repair grass or prove general graphics-device thread safety. The Linux WorldClient target built successfully with cmake --build build/linux --target WorldClient -j 4. The existing emergency allocator and job lifecycle tests also passed, but neither exercises terrain. Fake-backend terrain regression tests, actual rendering verification and the cost of serial terrain generation remain outstanding. This intentionally sacrifices terrain fill parallelism for correctness pending a safe measured design.

Stale validity simulation

multithreading-audit/emergency_mem_test.cpp models the former terrain fallback with the real shared staging allocator and simulated OpenGL upload and validity updates: two same-target locks alias, the first unfilled unlock uploads preexisting staging bytes and marks an already populated invalid buffer valid, and the readiness predicate then skips its refill. A sequential model checks that an invalid buffer is filled before its simulated upload. This checks the modeled mechanism, not RenderPrepBufs, the former fallback, or an actual graphics backend; those integration tests remain open. The Linux test passed ten consecutive CTest runs and one AddressSanitizer/UndefinedBehaviorSanitizer run.

Mixed direct/staging unlock simulation

Vulkan's IBufUnlock checks the target's shared emergency flag, rather than recording which mapping belongs to the buffer (Engine/Source/Gx/CGxDeviceVulkan/CGxDeviceVulkan.cpp:2802-2820). multithreading-audit/emergency_mem_test.cpp uses the real allocator and simulates a staging lock followed by a direct mapping on the same target: a direct-buffer unlock following that decision copies the staging bytes into the direct buffer and clears the flag. A sequential staging upload followed by a direct write retains both values. This is a model of the relevant branch, not a test of IBufLock, IBufUnlock, terrain, grass, or a graphics device; the backend trigger and actual runtime remain unverified. The Linux test target built, passed ten CTest repetitions, and passed a separate AddressSanitizer/UndefinedBehaviorSanitizer run. Actual fake-device integration, stale-validity coverage and backend testing remain necessary.

Shared staging reproduction

multithreading-audit/emergency_mem_test.cpp exercises the actual EmergencyMem implementation with malloc-based Storm allocator stubs: two equal-sized locks return the same pointer, writing through the second changes the first, and a single unlock clears the shared lock flag despite two prior locks. Both c++ -std=c++17 -O2 -I. multithreading-audit/emergency_mem_test.cpp Engine/Source/Gx/CGxDevice/EmergencyMem.cpp -o /tmp/wow-emergency-test && /tmp/wow-emergency-test and the same command with -O1 -g -fsanitize=address,undefined passed on Linux x86-64. This demonstrates the underlying staging behavior, not a terrain/grass regression test, graphics runtime reproduction, or repair. A larger second lock can reallocate the array; the test does not assume that a particular allocator moves it.

Grass staging mitigation and verification gap

DetailDoodad.cpp now fills and unlocks each vertex or index buffer before locking another, using the existing main-thread fill helpers. This removes grass's simultaneous same-target mappings and their associated worker writes; the 512 successful-batch limit remains. The change intentionally gives up parallel grass filling, with unknown frame-time cost. It assumes other code does not concurrently use the same graphics target and does not establish general device thread safety. The Linux WorldClient target built with cmake --build build/linux --target WorldClient -j 4; the existing emergency staging and lifecycle tests passed, but neither tests grass. Fake-device regression coverage, real backend rendering, and performance comparisons remain outstanding. Model loading is now invoked separately for vertex and index fills, as in the existing main-thread helpers; its performance effect is unmeasured.

Model CPU skin dispatch and doodad upload ownership

CWorldSceneRender.cpp:189-193 prepares skinning after scene animation. M2Scene.cpp:1922-1985 waits before clearing the global job vector and lookup, constructs distinct aligned offsets, resizes the byte vector before dispatch, and passes its stable job array to asynchronous SkinRange (M2Scene.cpp:1856-1883). CM2Scene::Draw calls M2SkinFinish before its pass test (M2Scene.cpp:1992-1994,2602-2607), and M2SkinTake uses the lookup only when ready (M2Scene.cpp:1997-2011). This establishes these particular vector lifetimes and output offsets under serialized main-thread scene use; it does not establish that referenced models, sections, bone matrices or transform implementations remain immutable during the overlap. Review intervening world updates, object destruction and all scalar/SSE/AVX transforms, and run a representative workload under a race detector before declaring the path safe.

The CPU doodad fallback is reachable when shaders are disabled and GPU drawing does not consume all instances; eight or more remaining instances use synchronous ParallelFor (CM2SceneRender.cpp:910-926,974-1002). The stack context and mapped vertex buffer remain live until completion; each index writes a separate 32 * vertexCount stride (CM2SceneRender.cpp:610-630,980-1017), and buffer unlock occurs on the caller after the join. Workers may read the completed skin cache or invoke a transform fallback. HYPOTHESIS: this partition is race-free if the mapped span is large enough, referenced data and function table remain stable, and all transform implementations only write the provided destination. Those conditions and backend support for worker writes to mapped storage are not yet verified. Validate against actual transform implementations, mapped-buffer contracts and a graphics runtime; no performance or runtime safety claim is made.

Animation root dispatch ownership

CM2Scene::Animate builds a process-global vector from animate-list entries with no attachment parent, passes a stack batch containing the vector and scene view into synchronous ParallelFor, then runs AnimateST and lighting only after that call returns (Engine/Source/Model2/M2Scene.cpp:2083-2125). The callback selects AnimateMTSimple or AnimateMT per root (M2Scene.cpp:228-248). Under serialized scene use, the batch and vector storage outlive the callback and the main-thread postprocessing cannot overlap it. Concurrent scene animation would instead mutate the shared root vector and is not established as supported.

Both animation variants update model-specific state and recurse through m_attachList after processing the parent (Engine/Source/Model2/M2Model.cpp:5457-5647,5812-6467). AttachToParent removes a model's prior attachment and links it under one parent (M2Model.cpp:6844-6885), supporting but not proving disjoint root trees during dispatch. The full variant also animates per-model texture, light, camera, ribbon and particle tracks, so its worker effects are broader than the nearby “own bones” comment suggests. HYPOTHESIS: worker writes are disjoint if attachment topology, per-model allocations, shared model data and scene state remain stable throughout dispatch and track helpers do not mutate shared state. Root-list uniqueness, attachment mutation/destruction by other threads, track helper side effects and asset loading remain to be verified. Inspect those paths and run a representative scene under a race detector before treating the animation path as safe; no runtime trigger, performance measurement or complete safety proof is claimed.

Lifecycle gap: non-Unix entry points do not shut down the pool

Confirmed API-level failure: the process-global pool contains joinable std::thread objects after Job::Init (Engine/Source/Base/Job/JobSystem.cpp:15-33,99-110); returning from main without Job::Shutdown destroys those objects and invokes std::terminate. The tracked job_exit_repro.cpp installs a terminate handler that exits 42. On Linux, compiling it with c++ -std=c++17 -O2 -pthread -I. multithreading-audit/job_exit_repro.cpp Engine/Source/Base/Job/JobSystem.cpp -o /tmp/wow-job-exit-repro yielded exit 42 without arguments and exit 0 with shutdown. This isolated process demonstrates the C++ lifecycle defect, not an actual client exit.

Unix and Android call Init, CommonMain, then Shutdown (WoW/Source/Linux/WinMain.cpp:33-42); Windows x86/x64 and Darwin return from CommonMain without those calls (WoW/Source/Win32/WinMain.cpp:30-36, WoW/Source/Win64/WinMain.cpp:29-36, WoW/Source/Darwin/WinMain.cpp:9-20). World initialization calls CMap::Initialize, which initializes terrain and the pool (WoW/Source/WorldClient/World.cpp:1857-1859, WoW/Source/WorldClient/Map.cpp:688-693, WoW/Source/WorldClient/MapChunk.cpp:283-285, WoW/Source/WorldClient/MapRenderChunk.cpp:264-265); repository source search found no production Shutdown outside the Unix entry point. Thus a normal return after reaching world initialization is a conditional source-level trigger on these non-Unix entry points; platform runtime behavior and whether client teardown always reaches normal process destruction have not been tested.

Candidate repair: pair lifecycle management at each supported client entry point, and verify shutdown occurs before callback-owned state is destroyed; do not merely rely on global destruction because cross-translation-unit destruction order and outstanding callbacks are unsafe. Add exit-process regression coverage and test supported Windows and Darwin builds and runtime shutdown. The current Unix shutdown is after CommonMain teardown, so whether an outstanding asynchronous skin batch can retain already-destroyed data remains an independent open question.

Non-Unix entry-point mitigation

Windows x86, Windows x64 and Darwin now call Job::Shutdown after CommonMain returns, without eagerly initializing the pool. This joins any pool initialized by world code before normal process destruction. Like the existing Unix ordering, it does not prove callback data survives the teardown inside CommonMain; asynchronous callback lifetime remains open. Abnormal process exits are not covered.

On Linux, cmake -S . -B build/linux, cmake --build build/linux --target job_exit_repro job_lifecycle_test -j 4, and ctest --test-dir build/linux -R '^(job_exit_shutdown|job_lifecycle_test)$' --output-on-failure --repeat until-fail:10 passed. The new process test verifies an explicitly initialized and shut down pool, not the platform entry points or game teardown. A Linux-hosted c++ -std=c++17 -I. -DWOWDECOMP_APPLE -fsyntax-only WoW/Source/Darwin/WinMain.cpp succeeded with a pre-existing multicharacter warning; this is not an Apple build. A MinGW x64 syntax attempt failed before reaching the changed code because Engine/Source/Base/OsCrt.h includes unavailable alloca.h; native Windows and Apple builds and runtime tests remain outstanding.

Skin batch completion along the world-frame path

CWorldScene::Render dispatches skinning only when World::s_m2Scene is non-null, then continues rendering before returning (WoW/Source/WorldClient/CWorldSceneRender.cpp:188-195,196-250). The normal world-frame caller invokes CWorld::Render, does additional work, reloads the scene pointer and returns if it is null; otherwise it invokes scene->Draw(M2PASS_0) (WoW/Source/Ui/WorldFrame.cpp:1787-1810; WoW/Source/WorldClient/World.cpp:774-776). CM2Scene::Draw calls M2SkinFinish before checking the pass mask, and Finish waits for the batch (Engine/Source/Model2/M2Scene.cpp:1992-1995,2602-2608). Thus this path joins before the first world-scene model draw if execution reaches that call with a non-null scene; another scene's draw can join earlier because the batch is global.

This is not a teardown safety proof: the caller has work and callbacks between dispatch and draw, and the null-scene return does not itself wait. CWorld::Destroy releases the world scene (WoW/Source/WorldClient/World.cpp:1799-1802), while entry-point shutdown occurs after CommonMain's event loop and teardown (WoW/Source/Client.cpp:1876-1881). Whether reentrant scene destruction or other model mutation is possible in the intervening calls remains unverified; no reachable use-after-free is asserted. Validate by tracing those calls and event reentrancy, and with an instrumented blocked skin callback during scene teardown; if destruction can overlap, join before the first affected model or scene resource is released.

Event teardown and skin ownership

The client registers DestroyEngineCallback as the event context's destroy handler (WoW/Source/Client.cpp:1795; Engine/Source/Event/EvtSched.cpp:791-792), and SynthesizeDestroy dispatches that event (EvtSched.cpp:281-295). When invoked, the handler calls ClientDestroyGame before CWorld::Destroy and M2Destroy (Client.cpp:1653-1667). Game destruction itself destroys object manager state and unloads the map before the world-scene release (Client.cpp:1604-1620; World.cpp:1620-1627,1750-1804). Scene release can delete the scene, whose destructor repeatedly releases its models (Engine/Source/Model2/M2Scene.cpp:1631-1640,2594-2597); skin callbacks dereference raw model and section pointers (M2Scene.cpp:1856-1883,1973-1985). The entry-point Job::Shutdown after CommonMain therefore cannot by itself establish that these objects remain alive until the join.

HYPOTHESIS: if destruction or model release is reentered while an asynchronous skin callback still holds those pointers, a use-after-free is possible. Neither that interleaving nor event-handler execution order relative to an active render has been demonstrated. In particular, a wait at scene release alone might be too late for resources destroyed by ClientDestroyGame. Trace the event scheduler and intervening rendering calls and reproduce with a blocked real skin callback and controlled teardown before selecting a join boundary. Static inspection only; no runtime test was performed for this finding.

Event scheduler ordering and reentrancy

The client initializes one event scheduler thread (WoW/Source/Client.cpp:1762); EventDoMessageLoop runs its scheduler on the caller (Engine/Source/Event/Event.cpp:42-44, EvtSched.cpp:683-715,734-765). On the ordinary scheduler path, input processing and queued events precede idle and paint, and a closed context is detached and destroyed only after those synchronous dispatches return (EvtSched.cpp:612-648). Paint dispatches registered layer callbacks synchronously (EvtSched.cpp:170-179, Engine/Source/Scrn/Layer.cpp:163-165,196-215,264). Consequently ordinary scheduler-driven destruction does not interrupt an in-progress paint on that scheduler stack; this is an ordering observation, not proof that all skin batches finish before teardown or that other threads cannot release models.

Reentrancy cannot be ruled out generally: initialization installs EventForceIdleProcessing as the OS poll callback (Event.cpp:15-26), which itself synchronously dispatches update, poll, queued events, idle and paint for the current context (EvtSched.cpp:190-219,306-320). Windows x86 and x64 install a timer for this callback during certain non-client menu messages (Engine/Source/Os/Win32/Input.cpp:1164-1165,1530-1535; Engine/Source/Os/Win64/Input.cpp:1136-1137,1494-1499). The inspected Linux and Darwin input files store the callback but contain no invocation. HYPOTHESIS: a modal message pump entered during rendering could permit nested dispatch; no path from the skin overlap interval to such a pump or concurrent teardown has been established. Trace intervening render calls and platform message pumping, then test with a blocked skin callback; do not treat a post-loop join as a resource lifetime guarantee. No runtime verification was performed.

Render work overlapping CPU skinning

After M2SkinPrepare starts a nonempty batch, CWorldScene::Render continues through terrain, portal, sky, entity and liquid work before returning; the frame then runs footprint and visible-unit/nameplate work before the model draw joins (WoW/Source/WorldClient/CWorldSceneRender.cpp:188-250; WoW/Source/Ui/WorldFrame.cpp:1787-1810). In that interval RenderEntitys may clear or update model culling flags and traverse attachments (WoW/Source/WorldClient/World.cpp:4729-4748,4768-4790). The scalar skin transforms read bone matrices, shared vertex data and the section and write their supplied output, rather than reading the culling flag (Engine/Source/Model2/M2Model.cpp:3803-3882); this particular flag update alone does not establish a race with those scalar transforms. The optimized skin path also reads skin batches, optimized ranges and section-enable pointers (Engine/Source/Model2/M2Scene.cpp:1855-1884). These observations assume the referenced objects remain alive and do not prove other transform variants or intervening call graphs safe.

PostAnimateVisibleUnits enumerates visible objects and either destroys a culled unit's nameplate or calls PostAnimate, which evaluates, updates or destroys a nameplate (WorldFrame.cpp:1531-1549; WoW/Source/Object/ObjectClient/Unit_C.cpp:814-821). No message pump or model release is established by this shallow trace; nameplate helpers, culling helpers, remaining render paths and platform callbacks still need transitive inspection. HYPOTHESIS: an unexamined helper could mutate or release skin inputs during the overlap. Validate with a controlled blocked real skin callback and race detection where available before selecting a synchronization boundary. Static inspection only; no runtime test was performed.

Terrain preparation and asynchronous file completion

Terrain reference construction is synchronously reached from CMap::PrepareUpdate: PreUpdateAreas calls UpdateArea only after the area's async object is cleared, then UpdateArea calls the area update that prepares chunks (WoW/Source/WorldClient/Map.cpp:2002-2006,2060-2086,1762-1766,2308-2321; MapArea.cpp:243-255). The same PrepareUpdate calls PrepareMapObjDefs, which can create WMO references (Map.cpp:2209-2228,2262,2320). Area async completion calls ProcessIffChunks and clears the async object (MapArea.cpp:344-352); the postload callback is invoked by the thread running AsyncFileReadPollHandler, after it removes the item under the queue lock (Engine/Source/Services/AsyncFile.cpp:125-146). The callback itself is not the chunk-reference creation chain, although its transitive texture-loading effects are not audited here.

One ordinary caller of PrepareUpdate is CWorld::Update, called by world-frame update (World.cpp:1632,1694; WoW/Source/Ui/WorldFrame.cpp:2130-2131). Other entry points include world load, preload and World::Update (World.cpp:1029-1058,1498-1517; Map.cpp:2540-2546,3017-3046); the latter is reachable from movement and preload has other callers. These chains execute on their caller, but the observations do not establish a universal thread affinity, exclude nested callbacks, or prove the preceding skin job was joined. HYPOTHESIS: an independent or reentrant caller could still overlap model construction with another constructor. Trace those callers and event/frame ordering, then reproduce the lazy-table race before changing it. Static inspection only; no runtime verification.

Terrain model creation and skin dispatch ordering

Terrain chunk reference creation can construct models: CMapArea::Update calls PrepareChunk, which calls CMapChunk::Create; Create calls CreateRefs, which calls the terrain overload of CMap::CreateDoodadDef, eventually invoking scene CreateModel (WoW/Source/WorldClient/MapArea.cpp:213-236,246-255; MapChunk.cpp:1197-1198,1241-1244,1258-1281; Map.cpp:2594-2642). WMO reference creation similarly reaches CreateModel through PrepareMapObjDefs and CMapObj::CreateRefs (Map.cpp:2209-2262,2686-2725; MapObj.cpp:2629-2656). These are synchronous call chains, but their top-level thread ownership and all possible invocations have not been established.

Detail-doodad model creation has a narrower ordering observation: on the ordinary world-render path, CullSortTable can call CullChunks, which calls chunk RenderPrep; enabled nearby detail doodads can then call LoadDetailDoodadModels, LoadModel, Load and CreateModel (World.cpp:4283-4318,4469; MapChunk.cpp:1330-1360,1596-1611; DetailDoodad.cpp:710-723,865-876). The CullSortTable calls in CWorldScene::Render occur before scene Animate and M2SkinPrepare (CWorldSceneRender.cpp:115-154,184-195), so this particular call chain completes before that render invocation launches its skin batch, assuming normal synchronous return. It does not rule out another scene, background loader, reentrant call, or an earlier outstanding batch. HYPOTHESIS: independent constructors could still race on the lazy transform table; establish thread ownership and reproduce concurrent first initialization before changing it. Static inspection only; no runtime or race-detector test was performed.

Model construction and particle animation ordering

Source search found the placement constructor in CM2ModelHeap::New (Engine/Source/Model2/M2Scene.cpp:214-225), called by both scene CreateModel and DuplicateModel (M2Scene.cpp:1513-1554). A successful constructor returns before scene initialization begins, including recursive duplicate initialization; this does not establish that independent callers are serialized. CreateModel is used in world, UI and particle code, and DuplicateModel in model attachment initialization and other game code. Thread ownership of all these paths remains unverified.

One important particle path is ordered: scene animation calls synchronous Job::ParallelFor before the subsequent AnimateST loop (M2Scene.cpp:2095-2116; Engine/Source/Base/Job/JobSystem.cpp:205-225). AnimateST invokes AnimateParticleST (M2Model.cpp:3120,3231-3245), whose emitter update can emit model particles and call CreateModel (M2Model.cpp:6579-6583, Engine/Source/Services/ParticleSystem2.cpp:1879-1886,1892-1955,2015-2028,535-573). Thus this scene path does not create particle models concurrently with its own animation batch, assuming normal return. This is not a global model-construction thread-safety proof: other scenes, callers, reentrancy and background loading have not been excluded. HYPOTHESIS: independent first constructors could race on the lazy function table, including observing entry zero before the rest are populated. Trace remaining creation paths and reproduce under a race detector before selecting a fix; no runtime test was performed.

SIMD skin transform ownership

WriteSkin selects a transform by bone influence and, for optimized geometry, walks enabled batch sections (Engine/Source/Model2/M2Scene.cpp:1824-1883). The SSE implementations fall back to scalar for unaligned output and otherwise read vertices and bone matrices, keeping blended rows local and writing the supplied output (Engine/Source/Model2/M2Model.cpp:3885-3960). AVX2's blend/cache and pair helpers likewise use caller-local rows and output pointers (Engine/Source/Model2/M2SkinAvx2.cpp:20-91,110-155). The vector stores temporarily overwrite adjacent fields inside each eight-float output vertex, subsequently overwritten by normal and texture stores; they do not extend beyond that vertex. These paths do not themselves mutate model state in the inspected code. This conclusion assumes valid section counts, indices, aligned bone matrices and disjoint correctly sized output regions, and does not establish source immutability or object lifetime during the overlap.

The function table is lazily initialized without synchronization in the model constructor (M2Model.cpp:4617-4640); a first model must already exist for a skin job to be prepared. HYPOTHESIS: concurrent construction during the first initialization could race on that table; constructor thread ownership and first-construction ordering have not been established. Verify model construction call paths and use a focused race test before treating this as a reachable defect or changing initialization. Validate the skin variants with representative model data and race instrumentation across the overlap; no runtime test or SIMD output equivalence measurement was performed here.
