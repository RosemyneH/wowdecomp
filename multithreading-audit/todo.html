Evidence added

The emergency staging test now simulates the Vulkan per-target unlock decision for a staging lock followed by a direct mapping: unlocking the direct buffer first consumes the shared staging bytes, whereas sequential staging and direct operations retain their distinct bytes. The actual allocator is used, but the backend and terrain/grass callers are simulated, so mixed-lock integration and stale-validity regression tests remain open. The Linux test built, passed ten CTest repetitions, and passed once under AddressSanitizer and UndefinedBehaviorSanitizer.

Animation dispatch analysis identifies synchronous stack/vector lifetime and parent-before-child traversal, but leaves root uniqueness, attachment mutation, shared track helper effects and runtime race detection open. See audit.html; no animation safety proof is claimed.

Static inspection of asynchronous model skinning and synchronous doodad CPU skin uploads documents vector lifetimes, per-job output offsets and join placement in audit.html. Referenced model lifetime, all transform variants, mapped-buffer worker-write contracts and runtime race testing remain unresolved; this is not a safety proof.

The lifecycle regression now covers synchronous fallback before initialization and confirms that both a subsequent Start and ParallelFor wait for a blocked prior batch before returning. The Linux test target built and ten consecutive CTest runs passed (cmake --build build/linux --target job_lifecycle_test -j 4; ctest --test-dir build/linux -R '^job_lifecycle_test$' --output-on-failure --repeat until-fail:10). The release thread uses a 20 ms delay, so this is a scheduling-dependent regression check, not a proof of all interleavings or concurrent API safety.

An initial synthetic benchmark exercises actual internal publication and waiting at 10, 20, 40 and 80 chunks with uniform, uneven and skewed workloads. Five samples per configuration show substantial variability; no scheduler improvement is claimed. The benchmark now also measures the public ParallelFor baseline and validates its output against the same serial reference; the different API paths and uncontrolled environment prevent an isolated chunk comparison. Other worker counts and representative workloads remain outstanding. See benchmarks.html and job_benchmark.cpp.

Grass fills now lock, fill and unlock each buffer before acquiring the next. The Linux WorldClient target built successfully; the existing emergency staging and lifecycle tests passed, but neither exercises grass. Fake-device and runtime coverage and performance measurements remain outstanding.

Terrain owned fills now use the existing serial RenderPrepBufs path, avoiding multiple outstanding locks of the same target within the queue. cmake --build build/linux --target WorldClient -j 4 passed. This is a compile check, not a terrain regression test or runtime verification; performance impact is unknown.

The actual emergency staging allocator's aliasing and single unlock flag are reproduced in emergency_mem_test.cpp, including an AddressSanitizer/UndefinedBehaviorSanitizer run. This does not exercise terrain or grass and does not resolve their outstanding lock-lifetime defects.

Completed

The emergency staging regression is registered with CTest and now checks that sequential lock/fill/copy/unlock cycles preserve distinct simulated uploads. On Linux, configuring with cmake -S . -B build/linux, building both regression targets and running ctest --test-dir build/linux -R '^(emergency_mem_test|job_lifecycle_test)$' --output-on-failure --repeat until-fail:10 passed all ten runs of each test. This exercises the real staging allocator but simulates the upload; it does not exercise terrain, grass, stale validity, mixed direct/staging locks, or a graphics backend.

The lifecycle regression is registered in CTest on non-Android builds, with a 60-second timeout. After cmake -S . -B build/linux, the job_lifecycle_test target built and ctest --test-dir build/linux -R '^job_lifecycle_test$' --output-on-failure --repeat until-fail:10 passed all ten runs on Linux. Android and other platform builds were not tested; the test does not establish concurrent API safety.

Shutdown now drains the active batch before stopping workers. Nonempty ParallelFor with a null callback is a no-op, consistent with Start; empty and null submissions do not wait. See audit.html for reproduction and test evidence.
